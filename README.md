## 1. Tell us about a problem you couldn't leave alone. What did you build to fix it?

Applying to jobs after graduation meant the same forty minutes of copying one resume into one form, hundreds of times, with no record of what I had sent where. I could not leave that alone, so I built JobOps: a pipeline that scans about 110 job feeds every morning through the Greenhouse, Lever and Ashby APIs, deduplicates against a persistent index, filters out roles I cannot legally take, ranks the rest with an explainable additive score where every number decomposes into readable reasons, tailors a one page resume per posting, and fills the application form in a visible browser that I review before anything is submitted. It keeps a JSON index, a markdown pipeline and a Google Sheet in sync and has carried more than 840 applications since June. The part I kept coming back to was trust: the first version quietly reported submissions it had never logged. Now every write reads itself back and a check at the end of each session fails loudly if the three stores disagree. The system is also the reason this application exists.

## 2. Tell us about a time you had to understand an unfamiliar system that wasn't behaving as expected. How did you get to the bottom of it?

In MIT's Equitable AI for Dermatology competition my team inherited transfer learning baselines that looked strong on the leaderboard and felt wrong. The task was classifying 16 skin conditions across the full range of skin tones, and the aggregate score hid the fact that the models were failing on darker skin, which was the entire point of the challenge. I stopped tuning and started measuring: per Fitzpatrick type accuracy, class balance per tone, what augmentation was actually doing to the underrepresented groups. The problem was representation, not capacity. I built targeted augmentation for the underrepresented types, moved the pipeline from CNN baselines to ViT and Swin transformers with phased training (freeze, then fine tune) and a weighted loss, and ran more than 200 Bayesian hyperparameter sweeps in Weights and Biases so the recipe was settled by evidence rather than taste. We finished at 76.3 weighted F1, first out of more than 240 teams. The lesson I kept: when a system misbehaves, measure where it fails the people it serves, not the average.

## 3. Describe a real coding task where AI tools helped you move faster. Where did you have to step in and think for yourself?

Most of JobOps was drafted with Claude Code: the Playwright autofill drivers, three ATS API clients, the scoring model, the Google Sheets bridge. That is how one person shipped a system with two dozen scripts and a test suite in a few months. The places I had to think for myself were the places the model could not see. It wrote a logging step keyed on a six character display id instead of the twelve character requisition key the index uses, so applied jobs resurfaced as new; the code was clean and the bug was invisible until I diffed the index against the tracker row by row. It wrote a summary that reported fields as filled without ever checking the page; I only caught that by reading the tabs myself. Architecture, the rules the system may never break (it cannot click submit, it cannot answer a work authorization question), and the decision that verification is separate work from doing were all mine. The model is fast at the first draft and blind to whether the draft was true, so my job became review, measurement and the questions it does not ask.
